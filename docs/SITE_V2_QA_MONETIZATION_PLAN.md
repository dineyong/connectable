외부 게시, 가입, 배포, 공개 SEO 설정, Git index 변경·commit·push·merge는 수행하지 않는다.

## 3. 후속 통합 검증의 시작 조건과 방법

기획 세션의 별도 요청을 받은 뒤 시작한다. 데이터·화면 담당 보고서가 있어야 하며 검증 대상 파일과
생성 관계를 특정한다: `data/site/content-v2.json` → 정적 표시 자산(있는 경우) → `web/` → 로컬 서버 → 브라우저.
검증 시작·종료 시 브랜치와 `git status --short`를 기록하고, 진행 중 파일이 바뀌면 영향을 받은 검증을 다시 한다.
동일 checkout이므로 브랜치/HEAD만으로 대상 버전을 고정했다고 주장하지 않는다. 대상 파일 해시와 실행 시각을 함께 기록한다.

데이터 계약은 schema_version, generated_on, monitors, reviews, guides, disclosures 및 각 콘텐츠의
안정적인 id, title, source_refs, review_status를 기준으로 한다. 계약 확장은 담당 보고서를 대조한다.
화면 데이터 로딩 방식은 실제 구현을 확인한다. 기존 `connect-src 'none'`를 완화하여 JSON fetch를 허용하는 방식은 승인 계약과 맞지 않는다.

검증 기록은 `ID / 대상 콘텐츠·화면 / 환경 / 절차 / 기대값 / 관측값 / PASS·FAIL·BLOCKED·NOT_RUN / 증거 / 후속 담당` 형식으로 남긴다.
스크린샷만으로 데이터 정확성을 통과 처리하지 않는다. 원본 대조, 응답·보안 헤더, 브라우저 동작을 함께 확인한다.
문제는 담당 파일 소유 세션에 기획 세션을 통해 전달한다. 이 품질 세션이 다른 소유 파일을 수정하거나 다른 세션에 메시지를 보내지 않는다.

## 5. 후속 실행 계획과 통과 조건

1. 데이터·화면 담당 보고서 및 생성 계약을 읽고 변경 범위를 확정한다. 기존 자료 보존본의 위치와 연결을 확인한다.
2. 새 데이터 검사·단위 테스트와 기존 Python 검사기를 실행한다. 생성기를 실행하면 소유 파일이 바뀔 수 있으므로 이 세션에서 임의 실행하지 않고 담당 생성 결과/읽기 전용 일치 검사를 사용한다.
3. `python3 -m unittest discover -s tests -q`, 정식 질문·공식 제품·pilot·Path Instance 등 기존 관련 검사기의 실제 존재·읽기 전용 동작을 확인한 후 실행한다. 실행 명령·개수·실패를 기록한다.
4. `tests/e2e/site-v2.spec.js`와 기존 mockup/review 테스트를 구현 변경 및 보존 경로에 맞게 대조한다. `npm run test:e2e`의 로컬 서버·환경을 확인하고 실행한다. 실제 광고를 호출하거나 클릭하는 테스트는 만들지 않는다.
5. 위 QA-01~25를 수동·자동 대조한다. 모든 모니터 기능/출처와 후기 요약의 핵심 결론은 원본에 대조하고 빈 상태·상세·긴 콘텐츠·민감정보는 경계 사례도 확인한다.
6. 기존 화면 보존본과 신규 화면의 회귀 결과, 데스크톱/모바일 증거, 잔여 위험을 이 문서의 후속 기록으로 남긴다.

잘못된 모델/사양/호환 표현, 출처 없는 확정, 개인정보 노출, 가짜 후기/사진, 금지된 광고·제휴 호출,
noindex/CSP 훼손, 주요 탐색·키보드 불능은 통합 통과를 막는 문제다.
통과에는 해당 문제 해소·필수 검사 통과·NOT_RUN/BLOCKED 범위 명시가 필요하다.
통합 통과도 공개 배포·검색 색인·실물 호환 승인·광고 계정 승인과 별개다.

## 8. 공개 SEO는 별도 단계

현재 로컬 목업은 noindex/nofollow를 유지한다. 이 표시는 접근 통제가 아니므로 비공개 정보 자체를 넣지 않는다.

공개 단계에서는 제목·설명·canonical·사이트맵·실제 HTTP 상태·404·robots/noindex 정책과
검색엔진이 읽을 수 있는 본문을 검증한다. 존재하지 않는 가격·재고·평점·리뷰 통계를 구조화 데이터로 넣지 않는다.
이 단계의 최신 검색 정책 확인과 운영 환경 검증은 아직 수행하지 않았다.
